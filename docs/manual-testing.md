# ALGA Exchange — пошаговая инструкция начинающему тестировщику

Дата подготовки: 29 октября 2026 года.

## Подключение с другого компьютера

Приложение запущено на компьютере разработчика. Оба компьютера находятся в общей локальной сети.

**Адрес для тестировщика: http://192.168.1.102:9000/#/auth**

- Не использовать `localhost` или `127.0.0.1`: на другом компьютере это адрес самого тестировщика.
- Компьютер разработчика должен оставаться включённым, dev-сервер — запущенным.
- На момент подготовки сервер слушает порт 9000 на всех IPv4-интерфейсах. Доступ именно с компьютера тестировщика ещё нужно подтвердить.
- Если страница не открывается, проверить общую сеть, разрешение входящих подключений на компьютере разработчика и отсутствие изоляции клиентов Wi-Fi. При смене локального IP заменить `192.168.1.102` во всех ссылках.
- Если приложение будет развёрнуто на другом адресе/порту, заменить базовый адрес в ссылках; пути после `/#/` сохраняются.

Backend: **https://admin.aminexpay.com**. Браузер отправляет запросы на `http://192.168.1.102:9000/api/...`; dev-прокси пересылает их на production backend. Локальный адрес в DevTools ожидаем.

Использовать свой аккаунт. Коды и персональные данные вводить непосредственно в приложении. KYC передаёт реальные данные, финансовые формы создают реальные заявки: выполнять отправки только в согласованном объёме.

## С чего начать, если вы раньше не тестировали приложения

Ваша задача — выполнить действия обычного пользователя, сравнить результат с ожидаемым и записать различия. Не нужно изменять код, вручную отправлять запросы или заходить в админку.

### Подготовка

1. Откройте Google Chrome или Microsoft Edge на своём компьютере.
2. Убедитесь, что подключены к общей сети с разработчиком.
3. Откройте адрес из раздела «Подключение с другого компьютера».
4. Если страница недоступна, сообщите разработчику точный текст ошибки браузера. Проверки приложения пока отмечайте `BLOCKED`, а не `FAIL`.
5. Подготовьте email, к которому у вас есть доступ, и согласованный аккаунт. Для регистрации нужен ещё не зарегистрированный адрес. Не используйте случайные чужие email и телефоны.
6. Для KYC отдельно уточните, чьи данные разрешено использовать. Для финансовых отправок уточните допустимые направление, сумму, реквизиты и число заявок.
7. Создайте документ результатов по шаблону в конце инструкции.
8. Запишите дату, время, версию браузера, ОС и адрес приложения. Версию Chrome/Edge можно посмотреть в меню браузера → «Справка» → «О браузере».

**Сначала проверяйте вход, профиль и переходы. К KYC и финансовым отправкам переходите только после подготовки данных.** Если данных или допуска нет, отмечайте `BLOCKED` и переходите к доступной проверке. Не создавайте новые аккаунты, SMS и заявки многократно ради повторения теста.

### Словарь

| Термин | Простое объяснение |
|---|---|
| Интерфейс / UI | Страница, поля, кнопки и сообщения, которые видит пользователь |
| Backend / API | Сервер, который принимает данные и возвращает результат |
| Запрос | Обращение браузера к серверу после открытия страницы или нажатия кнопки |
| GET | Обычно получение данных: профиль, курсы, состояние заявки |
| POST | Отправка данных: вход, код подтверждения, новая заявка |
| HTTP-статус | Числовой результат обращения к серверу, например 200 или 500 |
| Сессия | Состояние входа пользователя в приложение |
| Кэш | Уже загруженные данные, которые приложение временно хранит в памяти |
| KYC | Проверка личности пользователя |
| Котировка | Условия обмена с ограниченным сроком действия |
| Валидация | Проверка правильности введённых данных |
| Предусловия | Что должно быть готово перед проверкой: например, вход и одобренный KYC |
| Баг | Наблюдаемое отличие от ожидаемого поведения |

### Как смотреть запросы в браузере

1. Откройте приложение и нажмите `F12`. На Mac используйте `⌘ + Option + I`. Другой способ: меню браузера → «Дополнительные инструменты» → «Инструменты разработчика».
2. В открывшейся панели выберите **Network / Сеть**. Если вкладка не видна, найдите её в меню `»`.
3. Убедитесь, что запись включена: круглая кнопка записи обычно красная.
4. Выберите фильтр **Fetch/XHR** — он скрывает картинки, шрифты и прочие файлы.
5. Включите **Preserve log / Сохранять журнал**, чтобы запросы не исчезали при переходах.
6. Для обычного прогона оставьте **No throttling / Без ограничений**. Не включайте Offline случайно. Галочку **Disable cache / Отключить кэш** оставьте выключенной: настройки браузерного кэша здесь менять не требуется.
7. Перед отдельной проверкой нажмите кнопку очистки журнала. Она очищает только список запросов, а не аккаунт и сессию.
8. Выполните одно действие в приложении. Например, один раз нажмите кнопку входа.
9. В списке найдите строку нужного запроса. Можно ввести в строке фильтра `profile/me`, `onboarding` или другой фрагмент пути.
10. Нажмите на строку. В **Headers / Заголовки** найдите `Request URL`, `Request Method`, `Status Code`.
11. В **Payload / Полезная нагрузка** видно, что отправлено. В **Response / Ответ** или **Preview / Предпросмотр** — что вернул сервер.
12. Запишите метод, путь, статус и время. Не копируйте целиком вкладку Headers: там может быть секретный `Authorization`.

Если действие отклонено прямо в форме и запрос не появился, это может быть правильной валидацией. Например, при пустом обязательном поле сервер вызываться не должен.

`POST` со статусом `202` означает «принято в обработку», а не «перевод завершён». Успешный статус сам по себе тоже не доказывает, что интерфейс показал правильный результат: проверяйте и страницу, и ответ.

| Статус | Как трактовать при ручной проверке |
|---|---|
| 200 | Запрос успешно обработан; сравнить данные с интерфейсом |
| 201 | Создана запись/заявка; это не подтверждение исполнения обмена |
| 202 | Действие принято, обработка может продолжаться |
| 400 / 422 | Неверные данные; проверить понятность ошибки и возможность исправления |
| 401 | Нет действующей авторизации; после выхода ожидаемо, после корректного входа требует разбора |
| 403 | Нет разрешения на действие; проверить предусловия |
| 404 | Не найден объект; для KYC до начала onboarding может быть штатным состоянием |
| 409 / 410 | Конфликт состояния или недоступные условия; записать ответ, не угадывать причину только по числу |
| 429 | Слишком частые обращения; дождаться разрешённого повтора, не нажимать многократно |
| 500 / 502 / 503 / 504 | Ошибка сервера или промежуточного сервиса; сохранить факт и текст ошибки |
| `(failed)`, `pending`, отсутствующий статус | Запрос не завершён или проблема соединения; записать текст браузерной ошибки |

**Не используйте Replay XHR, Edit and Resend, Copy as fetch или ручной запуск запросов для этого прогона.** Все отправки выполняются кнопками приложения. Не отключайте сеть после финансовой отправки ради создания ошибки: результат может оказаться неизвестным, а операция — реально созданной.

### Как проводить один тест

1. Прочитайте предусловия и подготовьте нужную страницу.
2. Очистите список Network.
3. Выполняйте шаги по одному, дожидаясь результата каждого шага.
4. Сравните интерфейс и запрос с ожидаемым поведением.
5. Запишите `PASS`, `FAIL`, `BLOCKED` или `NOT RUN` сразу, не по памяти в конце дня.
6. Если найдена проблема, сохраните шаги и очищенные доказательства. Финансовый POST повторно не отправляйте только ради воспроизведения.

У одной страницы может быть несколько тестов. Например, правильный вход — один тест, неправильный пароль — другой.

### Рекомендуемый порядок

| Порядок | Что делать | Когда можно пропустить |
|---|---|---|
| 1 | Проверить доступ по локальной сети | Нельзя: без доступа остальные тесты заблокированы |
| 2 | Регистрация нового аккаунта или вход в согласованный существующий | Регистрацию можно отметить NOT RUN, если новый аккаунт не нужен |
| 3 | Профиль, переходы, кэш и курсы | Проверить до отправок KYC/денежных заявок |
| 4 | Выход, неправильный пароль, повторный вход | Использовать подготовленный аккаунт |
| 5 | Восстановление пароля | Только если разрешено менять пароль этого аккаунта |
| 6 | KYC | BLOCKED, если нет согласованных данных или подходящего состояния |
| 7 | Наличные заявки и инвойсы | Не отправлять без согласования реальной заявки |
| 8 | Безналичные операции | BLOCKED без одобренного KYC/условий/баланса или разрешения на операцию |

## 1. Регистрация

Страница: http://192.168.1.102:9000/#/registration

1. Ввести email, запросить код.
2. Подтвердить полученный код, установить пароль.
3. Проверить вход и загрузку своего профиля.
4. Проверить неверный код, занятый email, обязательные поля и повторное нажатие кнопки.

Запросы:

- `POST /api/auth/register/codes`
- `POST /api/auth/register/codes/check`
- `POST /api/auth/register/passwords`

Ожидается понятная ошибка при невалидных данных; переход дальше возможен только после успешного подтверждения.

### REG-01. Успешная регистрация — подробно

**Предусловия:** пользователь вышел из приложения; email ещё не зарегистрирован; почта доступна тестировщику.

| Шаг | Действие | Что должно произойти |
|---|---|---|
| 1 | Открыть страницу регистрации | Показано поле email; ввод пароля ещё не подтверждает регистрацию |
| 2 | Ввести свой новый email, один раз нажать кнопку продолжения | В Network появляется POST `/api/auth/register/codes`; интерфейс предлагает ввести код |
| 3 | Открыть почту и найти свежий код; при необходимости проверить «Спам» | Письмо относится к указанному email и текущей попытке |
| 4 | Вернуться, ввести полученный код и подтвердить | POST `/api/auth/register/codes/check`; после принятия кода открывается установка пароля |
| 5 | Ввести новый пароль и его совпадающее повторение, выполнить требования формы | POST `/api/auth/register/passwords`; при успехе загружается профиль и выполняется вход |
| 6 | Открыть профиль | Показан email созданного аккаунта, а не чужие или демонстрационные данные |

Не публикуйте пароль и код в отчёте. Если письмо не пришло, запишите время запроса и HTTP-статус. Не запрашивайте коды подряд без ожидания.

### REG-02. Ошибочные данные

Проверять по одному условию, каждый раз возвращая остальные поля к правильному виду:

- Пустой email и строка `abc` вместо email: нет перехода к следующему шагу, видна подсказка или кнопка недоступна.
- Один неверный код: нет перехода к установке пароля. Не перебирайте коды; несколько ошибок могут исчерпать попытки.
- Разные пароль и повторение: регистрация не завершается, отображается понятная подсказка.
- Изменение email или уход из регистрации: прежнее подтверждение не должно позволять завершить регистрацию другого адреса.

Для действий, которые отправляют письмо, используйте только согласованный адрес. Занятый email проверяется отдельно от нового аккаунта: ожидается корректно обработанный ответ без зависания и ложного входа.

## 2. Вход и сессия

Страница: http://192.168.1.102:9000/#/auth

1. Войти с правильным паролем.
2. Проверить неправильный пароль: ошибка, вход не выполнен.
3. Перезагрузить вкладку: сессия восстанавливается, профиль запрашивается с сервера.
4. Выйти через профиль: данные очищаются, защищённые страницы требуют входа.
5. Если пароль принят, но профиль загрузить не удалось, повторить загрузку: должен отправляться только запрос профиля, без повторного POST пароля.

Профиль загружается после входа до перехода на его страницу. При смене аккаунта данные прежнего пользователя не должны отображаться.

### AUTH-01. Правильный вход

1. Выйти из текущего аккаунта через профиль, если вход уже выполнен.
2. Открыть страницу авторизации и очистить Network.
3. Ввести email и текущий пароль своего аккаунта. Один раз нажать кнопку входа.
4. Найти `POST /api/auth/login`. После успешного ответа должен загрузиться `GET /api/profile/me`.
5. Открыть профиль: сверить email и статус проверки личности.
6. Обновить вкладку обычной кнопкой браузера. Повторный `POST /api/auth/login` не нужен; профиль восстанавливается через GET.

### AUTH-02. Неправильный пароль и выход

1. Выйти через профиль.
2. Ввести правильный email и заведомо неправильный пароль один раз.
3. Проверить: вход не выполнен, ошибка видна, кнопка после ответа снова доступна.
4. Войти с правильным паролем, затем снова выйти.
5. Вручную открыть адрес `/#/kyc` или `/#/exchange/cash`: ожидается страница входа, персональные данные не видны.

Не проверяйте перебор паролей и не пытайтесь вызвать блокировку аккаунта.

### AUTH-03. Восстановление загрузки профиля — дополнительный случай

Этот случай выполняется, **если сбой профиля произошёл сам или подготовлен разработчиком**. Не требуется специально ломать сервер.

1. Убедиться в Network, что login уже принят сервером, а GET профиля завершился ошибкой.
2. Нажать предлагаемую кнопку повторной загрузки профиля.
3. Проверить, что повторяется GET `/api/profile/me`, а не POST с паролем.
4. После успешного GET приложение должно показать свой профиль.

Если воспроизвести исходное состояние не удалось, отметить NOT RUN, а не PASS.

## 3. Восстановление пароля

Страница: http://192.168.1.102:9000/#/reset-password

1. Выйти из аккаунта, ввести свой email.
2. Запросить код, подтвердить его, установить новый пароль.
3. Проверить вход с новым паролем.
4. Проверить неправильный код и смену email: подтверждение прежнего email должно сбрасываться.

### RESET-01. Восстановление доступа — подробно

**Предусловия:** разрешено менять пароль этого аккаунта; вы знаете текущий пароль и имеете доступ к его почте; пользователь вышел из приложения.

1. Открыть страницу восстановления, ввести email, запросить код.
2. Проверить `POST /api/auth/reset-passwords/codes`. Дождаться письма.
3. Ввести свежий код, подтвердить. Проверить `POST /api/auth/reset-passwords/codes/check`.
4. Установить новый пароль и совпадающее повторение. Проверить `POST /api/auth/reset-passwords`.
5. При успехе проверить свой профиль, затем выйти.
6. Войти с новым паролем — ожидается успех.
7. Один раз попробовать прежний пароль после выхода — ожидается отказ. Если новый пароль совпал со старым, этот шаг неприменим: заранее используйте другой пароль.

**Ошибочные варианты:** пустой email, неверный формат, один неверный код, несовпадающие пароли. Для каждого ожидание — нет успешного завершения и есть понятная причина. После смены email старый код/подтверждение не должен применяться к новому адресу.

Не передавайте новый пароль в отчёте. Если после отправки нового пароля ответ потерялся, не делайте вывод «пароль не изменился»: уточните исход через обычный вход с согласованным паролем.

## 4. Профиль и кэширование

Страница: http://192.168.1.102:9000/#/profile

1. Проверить email, телефон при наличии и статус KYC.
2. Несколько раз перейти на главную и обратно.
3. Убедиться, что профиль отображается сразу: `GET /api/profile/me` не отправляется при каждом переходе.
4. Скрыть вкладку и вернуться: профиль обновляется в фоне без замены загруженных данных экраном загрузки.
5. Перезагрузить приложение: профиль снова запрашивается с сервера.
6. Выйти и войти другим аккаунтом: предыдущие данные не отображаются.

Редактирование профиля текущий API не предоставляет.

### PROFILE-01. Проверка кэша без ложных повторов

1. Войти, дождаться загрузки приложения и открыть профиль.
2. В Network поставить фильтр `profile/me`, очистить журнал.
3. **Внутри этой же вкладки** перейти на главную через интерфейс и вернуться в профиль. Повторить 3 раза. Не перезагружать вкладку и не переключаться в другую вкладку во время этого шага.
4. Ожидается: email и статус видны сразу; новых запросов `/api/profile/me` из-за этих переходов нет.
5. Очистить журнал. Переключиться на другую вкладку браузера, затем вернуться в приложение.
6. Ожидается фоновый GET профиля; ранее показанный профиль не заменяется полноэкранной загрузкой.
7. Очистить журнал и перезагрузить вкладку приложения.
8. Ожидается новый GET профиля: после перезапуска память приложения создаётся заново. Первичная загрузка в этом случае допустима.

Не считайте запрос после возврата из фоновой вкладки ошибкой кэширования — это отдельное ожидаемое обновление. Для проверки смены аккаунта нужен второй разрешённый аккаунт; без него отметить этот пункт BLOCKED.

## 5. Котировки

Страница: http://192.168.1.102:9000/#/

1. Проверить карточку «Курс обменов (1 USDT)».
2. Проверить покупку через СБП, продажу на карту и через СБП.
3. Проверить состояния загрузки, ошибки и ручное обновление.
4. Дождаться истечения котировки, в том числе в фоновой вкладке: истёкший курс скрывается.
5. При недоступности API демонстрационные цены появляться не должны.

Запросы: `GET /api/quotes`, `GET /api/rates`.

Для каждого разрешённого варианта выполнить отдельный тест. Если разрешена только одна операция, остальные проверить без отправки и честно отметить, что создание не проверено.

2. Зафиксировать время и результат исходного запроса.
3. После согласования с ответственным использовать только кнопку «Повторить тот же запрос» в текущей форме.
4. Сравнить в Network тело и `Idempotency-Key` двух попыток: они должны совпадать. Сравнение выполнять локально, не прикладывать секреты и реквизиты к общему отчёту.
5. Если котировка успела истечь, не выбирать новую для повтора неизвестной операции. Новый payload означает новое намерение, а исход прежнего сначала нужно выяснить.

Если форма уже закрыта и ключ потерян, не создавать новую операцию как замену неизвестной — уточнить состояние у ответственного.

Если вложенного баланса нет, используется общий баланс из `/api/balance` с соответствующей подписью. Суммы двух балансов не складываются.
4. Если есть `attributes.program`, условия конкретного клиента берутся из него. Default-значение `/api/referrals/commission` используется только как fallback.
5. Выбрать даты дохода и нажать «Применить». Проверить GET `/api/referrals/profit` с `filter[date_from]`/`filter[date_to]`. Начало позже окончания должно давать понятную ошибку.
6. Открыть «Мои рефералы»: GET `/api/referrals/relations`. Проверить пустой список либо фактическое количество приглашённых и распределённых наград. Сумму наград не путать с оборотом сделок клиента.
7. Открыть «История наград»: GET `/api/referrals/transactions`. Переключить тип записи: вкладки фильтруют загруженные строки локально, отдельного запроса с `filter[type]` не должно быть (production отклоняет его с HTTP 422). Если есть «Показать ещё», проверить следующие страницы. При наличии записи нажать «Подробнее»: должен загружаться GET `/api/referrals/transactions/{uuid}`.
8. Старые записи без валюты должны иметь пометку о неизвестной валюте. Для новой награды отдельно сверить полную сумму и фактически зачисленную часть в деталях; отменённая/ожидающая награда не должна выглядеть как завершённое зачисление.
9. При ошибке одного блока остальные успешные блоки остаются доступными. Ошибка не должна подменяться нулевым балансом.
10. Выйти из аккаунта: его данные очищаются. Гость на `/referrals` видит предложение войти. Для проверки другого аккаунта использовать только согласованный второй аккаунт.

Создание реферального вывода этим пакетом не подключено. Наличие минимума и комиссии в GET не означает работающую кнопку отправки заявки.

## Что пока не считать готовыми API-страницами

Старые `/wallet/deposit/*`, `/exchange/cash/confirm` и создание реферального вывода `/referrals/account/withdraw` остаются mock-only. В API-режиме ожидается страница недоступности. История и рефералы уже подключены к чтению API — проверять по разделам 10–11 выше.

## Фиксация результата

Для каждого сценария записать:

| Поле | Содержание |
|---|---|
| Страница и сценарий | Путь и проверяемое действие |
| Результат | PASS / FAIL / BLOCKED / NOT RUN |
| Шаги | Краткая последовательность воспроизведения |
| Ожидание / факт | Что должно было произойти и что произошло |
| Запрос | Метод, путь и HTTP-статус |
| Приложение | Скриншот или очищенный ответ ошибки |

Пароли, bearer-токены, SMS-коды, документы и полные платёжные реквизиты в отчёт не включать. Не пересылать неочищенный HAR или Copy as fetch с секретами.

Предыдущий GET-прогон относился к старому серверу и не подтверждает работоспособность нового production backend. На новом адресе отдельно подтверждён `GET /api/payouts/options` — HTTP 200; остальные результаты должен зафиксировать тестировщик.

Значения результата:

## Как написать понятный баг-репорт

Один баг — одно наблюдаемое нарушение. Не объединяйте «не приходит SMS», «не открывается профиль» и «не работает обмен» в один отчёт.

```md
# BUG-001. [Кратко: где и что произошло]

Связанный тест:
Дата/время и часовой пояс:
Страница:
Браузер/ОС:
Предусловия: вход выполнен/не выполнен, состояние KYC, прочие условия.

Шаги:
1. ...
2. ...
3. ...

Ожидаемо:
Фактически:

Запрос: METHOD /api/path
HTTP-статус:
Текст ошибки без секретов:
Повторяемость: один раз / каждый раз / не повторяли, чтобы не создать дубль.
Влияние: что пользователь не может сделать.
Приложения: скриншот/очищенный ответ.
```

**Учебный пример — это не утверждение о найденном баге:**

> BUG-001. При возврате с главной профиль снова показывает экран загрузки. Предусловие: пользователь вошёл, профиль уже загружен. Шаги: открыть профиль → в той же вкладке перейти на главную → вернуться в профиль, не сворачивая приложение. Ожидаемо: данные из кэша, без нового GET профиля. Фактически: экран загрузки и новый GET `/api/profile/me`, HTTP 200. Влияние: лишнее ожидание при каждом переходе.

Перед отправкой скриншота проверьте, что на нём нет пароля, кода, телефона, паспортных данных, полной карты или токена. При необходимости закройте эти области. На скриншоте Network не раскрывайте `Authorization`, а на скриншоте Payload — реальные персональные поля.

## Частые ситуации: что делать ученику

| Ситуация | Действие |
|---|---|
| Вместо приложения браузер пишет «Не удаётся получить доступ» | Проверить адрес и сеть, сообщить разработчику; дальнейшие тесты BLOCKED |
| Нет запроса после нажатия | Проверить ошибки полей, фильтр Network и включённую запись; если форма валидна и ничего не происходит, оформить наблюдение |
| Код не пришёл | Проверить свой email/телефон, папку «Спам», время и HTTP-ответ; ждать разрешённый повтор, не отправлять коды циклически |
| KYC уже находится на другом шаге | Продолжить с текущего состояния, не пытаться принудительно сбросить проверку |
| Нет котировок / 5xx | Записать точный запрос и ошибку, зависимую денежную проверку отметить BLOCKED |
| Финансовый POST завис или ответ потерян | Не создавать новую заявку; сохранить факт и уточнить исход |
| Не знаете, какой ответ правильный | Записать фактическое поведение и вопрос; не ставить PASS по догадке |
| После Offline перестало работать всё | Вернуть Network → No throttling, убедиться в подключении |
| В Network виден локальный IP вместо домена backend | Это нормальный dev-прокси, само по себе не баг |
| Ошибка только на локальном HTTP, в Console сообщение о недоступном browser API | Сохранить текст и передать разработчику; не отключать защиту браузера и не менять код |

## Когда прогон можно завершать

1. У каждого назначенного теста есть результат и комментарий к неполному покрытию.
2. Все FAIL оформлены воспроизводимыми шагами и очищенными доказательствами.
3. Все реально созданные заявки/операции учтены, неизвестные исходы отдельно переданы ответственному.
4. Не осталось случайно включённого Offline/ограничения сети.
5. Разработчику передан отчёт: что прошло, что не прошло и что не удалось проверить. Отсутствие данных для проверки не скрыто под статусом PASS.
